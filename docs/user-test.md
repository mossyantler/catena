## 2. 준비

```bash
npm install
npm run dev        # http://127.0.0.1:5180
```

| 방식 · 시나리오 | 주소 |
|---|---|
| Catena · roombook | `http://127.0.0.1:5180/?data=roombook#overview` |
| Catena · expense | `http://127.0.0.1:5180/?data=expense#overview` |
| 비교 기준 · roombook | `http://127.0.0.1:5180/?data=roombook&mode=baseline` |
| 비교 기준 · expense | `http://127.0.0.1:5180/?data=expense&mode=baseline` |

- 블록을 시작할 때마다 주소를 새로 연다(새로 고침). 두 화면 모두 위쪽에 데이터 출처 배지(`시뮬레이션 데이터 · <dataset_id>`)가 보인다.
- 정답은 기본 재생 위치(마지막 이벤트, 201 / 201) 기준이다. Catena 화면의 재생 위치 막대가 옮겨졌으면 다음 과제 전에 `끝으로`를 누른다.
- 화면 크기는 데스크톱(1440px 안팎)으로 맞춘다.

### 두 시나리오

| | roombook | expense |
|---|---|---|
| 도메인 | 회의실 예약 서비스 | 사내 경비 정산 서비스 |
| 생성기 | `scenarios/roombook.build.ts` | `scenarios/expense.build.ts` |
| `dataset_id` | `roombook-sim-1` | `expense-sim-1` |

두 묶음은 구조가 같다. WBS 깊이, 의존 모양, 차단 이유 종류, 수정 반복 Task, 양방향 집계 엣지를 만드는 두 요약 노드, Runtime 구성, 이벤트 순서가 같고, 도메인·이름·Task 번호·형제 순서가 다르다. 번호를 섞은 것은 첫 블록에서 본 번호를 외워 답하지 못하게 하려는 것이다. 구조가 같은지는 `tools/fold.test.ts`의 「사용자 시험: 두 번째 시나리오는 … 구조가 같다」 시험이 확인한다.

|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|
| roombook | T01 | T06 | T07 | T08 | T02 | T03 | T04 | T05 | T09 | T11 | T10 | T13 | T12 | T14 |

요약 노드: S1→S1, S11→S12, S12→S11, S121→S111, S2→S2, S3→S3.

## 3. 진행 순서(사용자 혼자)

측정표는 `docs/user-test-results.csv`이고 과제 문장이 들어 있다. 시험이 끝날 때까지 이 문서의 4절(정답)과 5절(오해 유형)은 보지 않는다.

1. **블록 1**: Catena · expense(`http://127.0.0.1:5180/?data=expense#overview`)를 새로 연다. 위쪽의 재생 위치 막대와 왼쪽 위의 "다른 프로젝트"는 누르지 않는다.
2. 측정표의 과제를 Q1부터 하나씩 읽고 화면에서 답을 찾는다. 과제마다 한 줄을 채운다.
   - 답(요약)과 판단 이유.
   - 이동 수: 보이는 화면이나 선택 범위를 바꾸는 동작(목록·그래프 항목 선택, 검색 결과 선택, 탭 전환, 뒤로 가기, 원문 창 열기)이 1회다. 스크롤, 확대, 마우스 올리기, 트리 펼치기, 검색어·거르기 입력, 창 닫기는 세지 않는다(명세 「이동 수 기준」).
   - 막힌 지점: 멈춘 곳, 헷갈린 화면 요소, 엉뚱하게 먼저 찾아간 화면과 그 이유. 없으면 비운다.
   - 탐색 시간(초)은 잴 수 있으면 적는다(참고).
   - 처음 보는 사람이 오해할 만하다고 느낀 표시는 메모에 적는다.
3. **블록 2**: 비교 기준 · roombook(`http://127.0.0.1:5180/?data=roombook&mode=baseline`)을 새로 열고 2를 되풀이한다.
4. 측정표를 Claude Code에 넘긴다. Claude Code는 정답, 기준 초과, 오해 유형 칸을 4·5절과 대조해 채우고, 기준 경로보다 많이 이동한 과제와 막힌 지점을 고칠 목록 후보로 정리한다. 고칠지는 사용자가 정한다(T07).

## 4. 과제와 정답

과제 문장의 `[ ]` 안은 시나리오별 Task다. 정답 판정이 애매하면 판정 기준대로 하고, 메모 칸에 이유를 남긴다.

### Q1 완료·진행

- **과제:** 지금까지 완료된 Task와 지금 실행 중인 Task를 모두 말해 주세요. 전체 완료 조건 가운데 몇 개가 인수됐는지도 말해 주세요.
- **정답**

  | | roombook | expense |
  |---|---|---|
  | 완료(인수됨) | T01, T06, T09 | T01, T02, T09 |
  | 실행 중 | T02(승인 단계), T07(구현·검증) | T05(승인 단계), T03(구현·검증) |
  | 인수된 완료 조건 | 8 / 29 | 8 / 29 |
- **판정:** 두 목록이 정확하고 수가 맞으면 정답. 실패한 Task(roombook T03, expense T06)나 취소된 Task(roombook T13, expense T12)를 완료로 넣으면 오답.
- **기준 경로(Catena):** 개요의 상태별 집계와 Task 목록. 이동 0회.
- **잘 나오는 오해:** M4(실행 종료를 인수 완료로 읽음), M6(완료 조건 수를 시간 진행률로 읽음).

### Q2 차단 이유와 해소 행동

- **과제:** [roombook: 인증 통합 테스트(T05) / expense: 영수증 처리 통합 테스트(T08)]는 왜 시작하지 못하고 있나요? 시작하려면 무엇이 먼저 일어나야 하나요?
- **정답**
  - roombook: 입력 슬롯 두 개가 아직 인수되지 않았다. T03 토큰 발급 구현의 `token_service`, T04 세션 관리 구현의 `session_service`. (더 거슬러 올라가면 T03은 실패해 사용자 결정을 기다리고, T04는 T02 인증 API 명세의 승인을 기다린다.)
  - expense: T06 금액 추출 구현의 `amount_parser`, T07 이미지 저장 구현의 `image_store`. (T06은 실패해 사용자 결정 대기, T07은 T05 영수증 API 명세의 승인 대기.)
- **판정:** 선행 Task 두 개를 모두 원인으로 들면 정답. 괄호 안의 연쇄는 맞히면 메모만 한다.
- **기준 경로(Catena):** 개요의 상태별 Task 목록에서 해당 카드 → Task 상세. 카드에는 첫 이유와 "외 1건"만 보이므로 이동 1회.
- **잘 나오는 오해:** M5(Phase 순서를 의존으로 읽어 "테스트 Phase라서 구현 Phase가 끝나야 한다"고 답함).

### Q3 의존과 병렬 가능

- **과제:** [roombook: 예약 API 구현(T07) / expense: 청구 API 구현(T03)]이 끝나야 시작할 수 있는 Task를 직접·간접 모두 들어 주세요. 그리고 이 Task와 동시에 진행해도 되는(서로 의존하지 않는) Task를 두 개 들어 주세요.
- **정답**

  | | roombook (T07) | expense (T03) |
  |---|---|---|
  | 후행(직간접) | T08, T10, T14 | T04, T11, T14 |
  | 병렬 가능(이 중 둘) | T02, T03, T04, T05, T11, T12 | T05, T06, T07, T08, T10, T13 |
  | 참고: 선행 | T01, T06, T09 | T01, T02, T09 |
- **판정:** 후행 셋이 빠짐·덧붙임 없이 맞고, 병렬 둘이 모두 위 집합 안에 있으면 정답.
- **기준 경로(Catena):** 개요 → 전체 의존 → Task 선택. 이동 2회.
- **잘 나오는 오해:** M1(Backend · Frontend 묶음과 그 방향별 개수를 순환이나 실행 순서로 읽음), M5.

### Q4 Manager·Worker 활동

- **과제:** [roombook: 예약 API 구현(T07) / expense: 청구 API 구현(T03)]에서 Manager는 무엇을 했고, 각 Worker는 무엇을 맡아 어디까지 했나요? Worker는 어떤 Agent Runtime으로 실행됐나요?
- **정답**

  | | roombook (T07) | expense (T03) |
  |---|---|---|
  | manager-1 (claude-code · claude-opus-5-5) | 일을 CRUD 핸들러와 시간 충돌 검사로 나눠 worker-1, worker-2에 맡김 | 일을 CRUD 핸들러와 월 한도 검사로 나눠 worker-1, worker-2에 맡김 |
  | worker-1 (claude-code · claude-sonnet-5-5) | CRUD 핸들러 구현을 마치고 제출, 단위 테스트 통과 | 같음(청구 CRUD) |
  | worker-2 (codex · gpt-5-codex) | 충돌 검사 구현 중 | 월 한도 검사 구현 중 |
  | 참고: reviewer-1 | API 계약 검토 중, "페이지네이션이 빠졌다"고 보고 | API 계약 검토 중, "반려 사유 필드가 빠졌다"고 보고 |
- **판정:** Manager의 분할·위임과 두 Worker의 담당·진행 정도가 모두 맞으면 정답. Runtime은 정답 판정에 넣지 않고, worker-2만 다른 Runtime(codex)이라는 것을 알아냈는지 메모한다.
- **기준 경로(Catena):** Task 찾기 결과 → Agent Graph → 노드 활동 기록. 이동 3회.
- **잘 나오는 오해:** M2(Worker의 "마쳤습니다" 보고를 검증 결과로 읽음).

### Q5 사용자 개입

- **과제:** 지금 사용자(승인자)가 승인하거나 결정해야 하는 일은 무엇인가요? 각각 무엇을 보고 결정하면 되나요?
- **정답**

  | | roombook | expense |
  |---|---|---|
  | ① 승인 | T02 인증 API 설계: 제출 S02-1의 보안 검토(T02-C2) 승인 또는 반려(A02-2) | T05 영수증 API 설계: 제출 S05-1의 개인정보 검토(T05-C2) 승인 또는 반려(A05-2) |
  | ② 결정 | T03 토큰 발급 구현: 수정 반복 상한(3회)에 닿아 Run이 실패. 실패한 검사 기록을 보고 새 시도를 시작할지 결정 | T06 금액 추출 구현: 같은 이유로 새 시도 여부 결정 |
- **판정:** 두 건을 모두 들고 각각 승인인지 결정인지 맞으면 정답. 이미 결정된 승인(roombook A01-1·A02-1·A06-1·A09-1, expense A01-1·A02-1·A05-1·A09-1)을 넣으면 오답.
- **기준 경로(Catena):** 개요의 "지금 결정할 일" 항목 → 결정 화면. 이동 1회.

### Q6 검증 근거

- **과제:** [roombook: 예약 API 구현(T07) / expense: 청구 API 구현(T03)]의 완료 조건은 어디까지 검증됐나요? 근거는 무엇인가요?
- **정답**
  - roombook: 완료 조건 3개 중 T07-C1(예약 CRUD 단위 테스트)만 검증 통과(아직 인수 전). 근거는 검사 코드(test-runner)가 남긴 증거 E07-1, 로그 `PASS 3 of 3`. T07-C2(충돌 테스트)와 T07-C3(API 계약 일치 검토)는 미검증. reviewer-1의 "응답 형식은 API 계약과 일치한다"는 Agent 보고라 증거가 아니다.
  - expense: T03-C1(청구 CRUD 단위 테스트)만 검증 통과, 증거 E03-1. T03-C2, T03-C3 미검증. reviewer-1의 판단은 Agent 보고.
- **판정:** C1만 검증 통과(인수 전), C2·C3 미검증으로 답하고 근거로 검사 로그(증거)를 들면 정답. C3를 Reviewer 보고로 검증됐다고 하면 오답이고 M2로 적는다.
- **기준 경로(Catena):** Task 찾기 결과 → 완료 조건의 증거. 이동 2회.
- **잘 나오는 오해:** M2, M4.

### Q8 실패·수정 반복

- **과제:** 검증에 실패해 고친 뒤 다시 시도한 Task는 어느 것인가요? 각각 몇 번째 시도까지 왔고, 지금 어떤 상태인가요?
- **정답**

  | | roombook | expense |
  |---|---|---|
  | ① 반복 중 실패 | T03 토큰 발급 구현: Agent 3회차(수정 2회), 자동 검사 3번 모두 실패, 상한에 닿아 Run 실패, 사용자 결정 대기 | T06 금액 추출 구현: 같음 |
  | ② 고쳐서 인수 | T06 DB 스키마 설계: 2회차(수정 1회)에 검사 통과, 인수됨 | T02 청구 테이블 설계: 같음 |
- **판정:** 두 Task와 회차가 맞으면 정답. 3회차의 Worker 보고("모든 테스트를 통과했습니다")를 믿고 통과로 답하면 오답이고 M2로 적는다.
- **기준 경로(Catena):** Task 찾기의 `수정 반복 있음` 필터 → Task 상세의 Run 이력. 이동 2회.

비교 기준 화면에는 기준 경로가 없다. 한 화면에 목록과 로그가 있으므로 이동은 대부분 원문 창 열기다. 실제 이동 수만 적는다.

## 5. 미리 정한 오해 유형

| 코드 | 오해 | 드러나는 말의 예 |
|---|---|---|
| M1 | 집계 엣지를 순환이나 실행 순서로 읽음 | "Backend와 Frontend가 서로를 기다려서 막혀 있다", "Backend가 끝나야 Frontend를 한다" |
| M2 | Agent 보고를 검증 결과로 읽음 | "Worker가 테스트를 통과했다고 했으니 통과", "Reviewer가 일치한다고 했으니 검증됨" |
| M3 | 시뮬레이션이나 기록 재생을 실제 실행으로 읽음 | "지금 Agent가 돌고 있다" |
| M4 | 실행 상태 `종료`를 인수 완료로 읽음 | "Run이 끝났으니 완료" |
| M5 | Phase를 WBS 상위 단계로 읽음 | "설계 Phase가 끝나야 구현 Phase를 시작한다", Phase로 의존을 판단함 |
| M6 | 검증된 완료 조건을 시간 진행률로 읽음 | "8 / 29니까 30% 정도 시간이 지났다", "남은 기간은 …" |
| M7~ | 새 유형 | 위에 없으면 새 번호를 매기고 이 표에 더한다 |

- 답이 맞아도 이유에서 잘못된 해석이 드러나면 적는다. 한 과제에서 여러 유형이 나오면 모두 적는다.
- 참가자가 설계자라 본인이 오해하기보다 처음 보는 사람이 오해할 만한 표시를 알아채는 일이 많다. 메모에 적은 그런 표시도 해당 유형으로 적는다.

## 8. 보조 확인(통과 조건 아님): CLI JSON만 쓰는 Coding Agent

Coding Agent 하나에 CLI의 JSON 출력만 주고 같은 과제를 풀게 해 정답률을 기록한다. 화면이나 묶음 파일은 주지 않는다. 시나리오마다 한 번씩 한다.

```bash
node tools/catena.ts status --bundle scenarios/roombook --json
```

| 과제 | 쓸 수 있는 명령(묶음은 `--bundle scenarios/<이름>`) |
|---|---|
| Q1 | `status` |
| Q2 | `status`, `show <Task>` |
| Q3 | `graph`, `ready`, `show <Task>`(`relations`: 선행·후행·독립) |
| Q4 | `agents <Task>`, `activity <Task> <노드>` |
| Q5 | `inbox`(승인 항목은 `approval`에 승인 범위), `raw <sha256:원문>` |
| Q6 | `show <Task>`, `activity <Task> <노드>`, `raw <sha256:원문>`(검사 로그 본문) |
| Q8 | `status`(`rework`), `show <Task>`(`runs`: `run_attempt` Run 시도, `agent_round` Agent 회차, `repairs` 수정 횟수) |

틀린 과제는 JSON 형식 수정의 입력으로 쓴다.
